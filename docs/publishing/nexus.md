# Publishing on Nexus Mods

We publish on Nexus only (for now): **one page per mod** + **one "MC Valheim - All Mods" pack page**. The pack can
go first: the 0.9.0 public preview and the 1.0.0 release publish only the pack page (`-PackOnly`), and the single
mod pages come later (user decision, 2026-10-17; see section 4). Everything to upload is generated by `./tools/Package-Mod.ps1` into `dist/nexus/`; nothing
is uploaded automatically. Facts below were checked against the Nexus upload form, help pages and the Vortex source in
September 2026 (see `docs/research/` for the research notes).

## 1. Prepare the release

1. Every in-game test for the version passes (`./tools/Get-TestTodo.ps1`). Untested items can only ship with
   `-AllowPending`, and they are then listed on the page sheet.
2. Set the release version in the mod's csproj (`<Version>`) and make sure its `CHANGELOG.md` has a `## x.y.z`
   entry for it (one line per change; Nexus shows changelogs one line per entry). **The first release of a mod is
   1.0.0**, with a `## 1.0.0` entry ("First release."); the 0.x entries below it are the pre-release history. A first
   release can also be a **0.9.0 public preview** ("First public release."; the pack went out that way on 2026-10-17,
   alone and without pictures, before a 1.0.0 with the final page). Before
   the first release every change already raised the version (0.1.0, 0.2.0, 0.2.1, ...), so each test build has its
   own number. After it, the first change after a release raises the version, so it is usually already set.
3. Pack: same in `packaging/nexus/pack.json` (`version`) and `packaging/nexus/PACK_CHANGELOG.md`; its first release
   is 1.0.0 (or a 0.9.0 preview) too. Released with `-PackOnly`, the pack holds every shipped mod at its own version
   (0.x is fine there); the pack tag lists them, so a packed mod counts as released at that version: change its code
   later and its version must go up (the release gate checks it).
4. Commit, then run `./tools/Package-Mod.ps1 -Release` (all mods + pack), `-Release -PackOnly` (the pack alone, see
   section 4) or `-Mod X` for one mod (no pack then: the pack always contains every shipped mod, see "Keeping a mod
   out of a release" below).
   The release gate refuses: a dirty git tree, a missing changelog entry, failed tests, untested items (mod and
   framework tests, without `-AllowPending`), names/versions/texts that break Nexus rules, a pack version already
   released, a first release (mod or pack) that is not 0.9.0 or 1.0.0, a version that is not above the last released one,
   and a mod whose code changed since its released version (raise its version). A mod already released
   and unchanged is simply reused in the pack. On success it creates local tags `nexus/<GUID>/v<version>` and
   `nexus/pack/v<version>` (all or nothing). A dry run of an already-released version writes to `<version>-dev`,
   never over the released files; a sheet built from uncommitted changes says "do not upload".

### Keeping a mod out of a release

A mod that is not ready (for example one that needs a rework after a game update) can stay in the repository
without being published. Mark it in its csproj:

```xml
<ModShip>false</ModShip>
<ModShipNote>Needs a rework for Valheim 1.0.20. Left out of the release until then.</ModShipNote>
```

- `Package-Mod.ps1` (dry run and `-Release`) then skips it and prints its name and the note: no page files, no tag,
  and it is not in the pack. The pack's page sheet lists it under "Left out of this pack". The pack check compares
  the pack with the shipped mods only.
- `ModShipNote` is required when `ModShip` is `false`, and `ModShip` only takes `true` or `false` (leave it out to
  ship the mod): the build refuses anything else (spaces around the value are ignored, by the build and the tools
  alike). `Package-Mod.ps1` also refuses a shipped mod whose `ModRequires` names a mod that is left out: ship both or
  neither.
- The mod still builds, deploys to the game and runs its self-tests like every other mod. `./tools/Get-Mods.ps1`
  shows `Ship = False` for it, and `./tools/Get-TestTodo.ps1` marks its tests as not a release gate.
- To ship it again, remove both lines (or set `<ModShip>true</ModShip>`), give it its release version and
  CHANGELOG entry, and add it to the next pack version's `PACK_CHANGELOG.md` entry.

Left out today: Cheated Tag Remover (`MC.UX.CheatedTag.Remover`), until its rework for Valheim 1.0.20.

## 2. Create or update the page

Open `dist/nexus/<GUID>/<version>/nexus-page.md` (or `_Pack/<version>/`). It lists every value to enter:

| Step | What to do |
|---|---|
| General | Name, author (`MC`), version, category (suggested), summary (plain text, max 350), tags. |
| Description | Switch the editor to **source mode**, paste `description.bbcode.txt`, check the preview. |
| Media | Upload `thumbnail.png` (16:9) and set it as thumbnail; `header.png` (1300x372) as page header (optional). Real in-game screenshots are better: add them when you have them. |
| Requirements | Add **BepInExPack_Valheim** (https://www.nexusmods.com/valheim/mods/3605) as a file-to-file requirement on the main file, minimum 5.4.2350. For MC dependencies, add the required MC mod's main file. |
| Permissions | "Use recommended settings" or your own. Third-party content: No. |
| Files | Upload the zip. First time: **Add as new file**. Later: **Update existing file** (the previous main file) + **Archive existing file**. Keep the file **name** stable and without version (Vortex uses it to detect updates). Category: Main. Tick "Update mod version to match this file's version". |
| Changelog | Add the lines from the sheet under the version. |

To publish, Nexus needs: name, author, version, category, summary, a description different from the template,
at least one gallery image set as thumbnail, and at least one non-archived file.

After the first publish, put the page URL in `packaging/nexus/pages.json` (by GUID, or `pack`). Later packages
then cross-link: each mod's description links to the pack, the pack lists each mod's page. While an included mod has
no URL there, the pack's description, README, file description and Vortex line say manual install only and send
nobody to single mod pages; the first package after every included mod has a URL tells Vortex users to install the
single mods instead, by itself.

## 3. AI tags (mandatory)

Nexus requires correct **Generative AI Usage** tags and moderates wrong or missing ones. Our tags (decided
2026-09-28):

- **AI Assisted**: development is led by the author (design, decisions, in-game testing) with AI help on the code.
  Nexus only accepts this tag with visible evidence of human-led development: development history, commit
  history or design notes, and the author must be able to explain the mod if asked. Keep such evidence on or linked
  from the page, otherwise moderators may switch the tag to "AI-Generated Content". `packaging/nexus/about.md`
  ("How these mods are made", with the GitHub link) is added to every page description and the pack README by
  `Package-Mod.ps1` for that reason (user decision 2026-10-17).
- **AI Media**: the description text and the placeholder images are AI-made. Pictures chosen for the pack go in
  `packaging/nexus/images/pack/` (`thumbnail.png`, `header.png`, `gallery/`) and are used instead of the
  placeholders (the 0.9.0 preview had none: the user makes the 1.0.0 pictures); check whether the tag still fits
  them before choosing it.

Never publish a mod whose in-game tests have not been run: untested AI mods are treated as spam.

## 4. The pack

- One flat zip with every shipped mod (not the ones with `ModShip` false), same folders as the single downloads (so
  both can overwrite each other safely).
- **Allow mod manager download: No.** Vortex's community Valheim extension installs only the first DLL folder of
  an archive, so a Vortex user would silently get one mod out of the pack. Until every included mod has its own
  page, the pack page tells Vortex users to install the pack by hand; after that, to install the individual mods
  instead (section 2). A Nexus Collection of the single mods is the Vortex-native alternative (created from Vortex,
  later).
- **The pack can be published before the single mods** (0.9.0 and 1.0.0: the pack page only).
  `./tools/Package-Mod.ps1 -Release -PackOnly [-AllowPending]` builds and checks every shipped mod (CHANGELOG entry
  for its version, tests, Nexus fields) and packs it at its own version, but writes no single-mod page files and no
  `nexus/<GUID>/v<version>` tag; only `nexus/pack/v<version>` is created, and its message lists every packed mod
  with its version. That list is what makes a packed mod "released" at that version: a later release refuses it if
  its code changed since without a new version, and `Update-Backlog.ps1` shows it as released. A mod's own page
  later is its own first release (1.0.0). Without `-PackOnly`, `-Release` tags every shipped mod and writes its
  page files too; keep those `dist/nexus/<GUID>/<version>/` folders: a later `-Release` reuses a released,
  unchanged mod in the pack without rebuilding its page files, and a dry run of a released version writes to
  `<version>-dev` ("do not upload"). The pack's page sheet
  shows which included mods have a page ("Own page" in Contents), and its checklist asks for matching versions only
  on the pages that exist.
- Framed as a convenience bundle of our own mods (Nexus asks compilations to be more than a repack; our pack holds
  only our own mods, from the same author, and the same files as the single pages once they exist).

## 5. How players end up installing

| Method | Result |
|---|---|
| Manual (extract into the Valheim folder) | `BepInEx/plugins/MC_Valheim/<Category>/<GUID>/` |
| Vortex, single mod (once it has its own page) | `BepInEx/plugins/<GUID>/` (the Valheim extension flattens folders; the mod works the same) |
| Vortex, pack | Disabled (see above) |

Players should not mix a Vortex install and a manual install of the same mod (two copies of one GUID: BepInEx
loads only the newest and warns). Settings always live in `BepInEx/config/<GUID>.cfg`, whatever the method.

## 6. Rules to keep in mind

- Never ship game files (no Valheim or Unity DLLs, no publicized assemblies, no game assets). Our zips contain
  only our DLL, README.md, CHANGELOG.md and the mod's own Content files.
- Never ship `winhttp.dll`, `doorstop_config.ini` or anything under `BepInEx/core`, and never name a folder or
  zip "BepInExPack...Valheim": Vortex would treat the archive as a BepInEx pack.
- No zips inside zips, no password-protected archives (Nexus quarantines them).
- Names: letters, digits, space and `_ ' ( ) . -` only. File name max 50, summary max 350, file description max
  255, version letters/digits/`.`/`-` only. The pipeline checks these.
- No advertising other sites, no asking for endorsements or donations, no unproven performance claims.

## 7. Automating uploads later (not set up)

Nexus has an official Upload API (v3, https://api-docs.nexusmods.com/) and a GitHub Action
(Nexus-Mods/upload-action). They can **add new versions to an existing file** and changelogs, authenticated with
your personal API key. They cannot create pages or edit page text, so the first release of every page stays manual.
The mod-file endpoints are marked experimental. When there are several pages to update regularly, a
`tools/Publish-Nexus.ps1` using the key from an environment variable could upload new versions in one command.
